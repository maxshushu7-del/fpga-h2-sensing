# 报告诊断工作流与可复制提问

## A. 先建立可比较的基线

提供本任务的器件、工具版本、目标时钟、源代码/参数版本、约束和报告。建议至少有：时序汇总及失败路径、利用率、时钟/未约束路径检查、DRC/CDC；针对具体问题补充对应报告，不为收集而收集。

报告命令/字段应按自己的 Vivado 版本核实，本包没有完成跨版本命令验证。缺少某项写缺失，不把空白解释为零违规。

可直接向 AI 提问：

> 先不要改代码或约束。根据这些报告填写报告卡片：报告阶段/版本、设计目标、实际失败路径、已约束范围、资源分布与证据缺口。每个结论指向具体报告位置。区分已证实事实和假设，尤其检查为什么这条路径应该被当前时钟/例外约束覆盖。只有汇总数字时，不凭空确定根因。

## B. 分类并安排有区分力的检查

| 证据/症状 | 候选方向 | 下一步需要的证据 |
|---|---|---|
| setup 失败、组合级数深 | 算术/优先级链、位宽、运算复用 | 代表路径及功能/延迟契约，能否合理流水化 |
| 逻辑浅、布线占比高 | 扇出、拥塞、布局/资源组织 | 扇出/路径及物理分布，不能只删逻辑 |
| 端口或源同步接口失败 | 发射/捕获关系、相位、板外延迟依据 | 实际接口与约束来源、setup/hold 两侧结果 |
| WNS 非负但存在未约束路径 | 检查覆盖不完整 | 时钟、I/O、例外和路径覆盖的审查，不先庆祝通过 |
| 资源骤增 | 位宽扩展、运算实例数、存储推断等 | 同一器件/配置下模块级资源对比及需求 |
| CDC 告警 | 实际同步结构、握手保持、复位释放 | 接口结构和协议证据，不能统一豁免全部异步路径 |
| 工具崩溃/内部异常 | 工具/流程/检查点问题，原因待定 | 完整日志、版本和可复现步骤，不将崩溃当功能反例 |

> 针对最可能的原因给出证据链、尚不能排除的另一种解释和最小区分测试。列出可选修正及对延迟、吞吐、资源和风险的影响。不要把放宽约束作为默认修复；如果需要例外，先证明协议/电路条件，并说明如何验证覆盖范围。

## C. 最小修正与回归

> 仅在本轮授权范围内实施选定的最小修正，保留可回退基线。列出必须重跑的功能、时序和接口检查。实际运行后逐项报告，未运行的标为未验证；不要只输出一张“最终通过”的汇总。

典型约束：

- 运算流水化：更新输出延迟契约、对齐 valid/数据/状态，再运行数值及协议回归。
- 时钟或相位：检查 setup 和 hold、相关端口/时钟组及实际配置；具体相位不跨器件照搬。
- 约束补全：说明依据从哪里来，先确认模型是正确/暂定/未知，而不是只看指标是否好看。
- 资源优化：同一配置下比较功能、性能和资源，确认没有以吞吐或数值精度换取未声明的节省。
- 检查点/ECO：区分从源重建和检查点修改，保存对应参数、来源和报告；不可把两种流程的结果混写。

## D. 输出不能只写 PASS

结论至少区分：功能验证结果；当前模型下实现结果；未决告警；板外模型依据；实板情况。若核心证据不足，给出补充项和停止条件，不继续凭猜测连改多处。

迁移证明需在自己的新题目上执行，保存前后报告及原始日志。本源项目的板卡、时钟和相位不是通用参数。
